# DeepSeek 命令件

**哑管道**：把调用原样发给 DeepSeek、把结果原样带回——不重试、不熔断、不缓存。
降级策略全在调用方，别指望这件替你扛。

## deepseek.chat

`{ prompt, system?, jsonMode?, timeoutMs?, caller?, model? }` → 成功回
`{ text, usage:{ promptTokens, completionTokens, totalTokens }, model, caller }`。

- **caller 自报家门**（如 `"news-links"`、agent 自己的名号）——进记账，缺省 `adhoc`
- `jsonMode: true` 要求 prompt 里出现 `json` 字样（DeepSeek 官方约束，否则 400）
- `timeoutMs` 缺省 60000，上限 110000（命令总线 120s 红线之内）
- `model` 缺省走设置的 `deepseek-chat`；要推理模型传 `deepseek-reasoner`

失败回 `{ ok: false, error: <kind>, detail }`，四类：

| error | 意思 | 调用方该干什么 |
| --- | --- | --- |
| `timeout` | 等到超时上限没回 | 大 prompt 拆小或调大 timeoutMs，别原地连发 |
| `rate_limit` | 429 | 自己退避，件不管 |
| `bad_key` | 401/403 或 key 没配 | 查设置，别循环重试 |
| `bad_response` | 5xx / 应答畸形 / 网络不通 | 看 detail；偶发可重试一次，连续出现是环境问题 |

另有 `bad_args`：参数本身不合法，detail 里说原因。

## deepseek.usage

`{ days? }`（缺省 30）→ `{ byCaller:[{ caller, calls, ok, failed, totalTokens }], total }`。
记账含失败调用（`failed` 计数、无 token）——「模型连续降级 N 轮」这类判定从这儿取材。
账本最多留 500 条，老的先滚出去。

## 设置

`api-key`（secret，必填）、`model`（缺省 `deepseek-chat`）、`base-url`（缺省 `https://api.deepseek.com`）。
key 不随包发、不进日志；换 key 只改设置，不动件。

## 调用方纪律

- 本件记账落盘失败只 warn 日志、不改回执——成功调用的结果不因记账丢
- prompt 内容与应答正文都不进日志，日志里只有 caller / model / token 数
