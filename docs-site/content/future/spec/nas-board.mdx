边界：NAS 侧的生产（采集 → 判定 → 归档定案 JSON，每天 07:00 自己跑一轮）与部署的正本都在
ugreen-nas-config（单元 26091409bfn），部署到 NAS 上也在那边做；本插件只消费。契约是定案 JSON
（schema 正本 `ugreen-nas-config/src/nasreport/schema.py`，v2；v1 旧格式读入时升成 v2 的形状，但**旧的历史归档不接**，
2026-09-20 定下，看板从部署那天起从空开始）。

## 验收

- [ ] 数据源：经 SMB 的 UNC 路径只读拉归档目录（路径是设置项）；拉不到时看板明确显示「取数失败」，不静默
- [ ] 看板：今日一行结论 + 三色总评 + 异常项表 + 近 30 天可用性竖条
- [ ] 新鲜度看门狗在顶部亮黄：最新日期早于今天（且已过 NAS 出报告的时刻）、seq 断号、schema 版本认不出
- [ ] 每天自动刷新一次 + 手动刷新按钮；插件里放不了常驻定时器时，改为「打开窗格时发现数据过期就拉」（体验一样）
- [ ] 视图每次从 JSON 重新画，判定与结论一律取归档里的原值、不重算
- [ ] 一键复制询问：当天的定案压缩成结构化文本，加一句「帮我解读」的 prompt，整段放进剪贴板
- [ ] 在隔离 home 里用 PC 上回放的归档（ugreen-nas-config 的 `out/nasreport-fetch` 快照）真数据验一轮
- [ ] `pnpm check` 全绿

## 方案

命令 `nas-board.refresh` / `nas-board.status` 加一个窗格。定案 JSON 的解析与 v1 的升格在 TS 侧自己实现（python 侧的
`schema.py` 是对照的正本，不引 python、不跨仓 import）。没有模型、没有推送、没有渲染服务——为什么这样定，见轨迹卡
[弃推转拉](/trajectory/2026-09-20-pivot-to-gwb-consumption)，ugreen-nas-config 的草稿里也有同一次转向的记录。
