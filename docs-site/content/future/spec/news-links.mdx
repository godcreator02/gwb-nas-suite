定下的要点（2026-09-20，方案甲）：**只做 gwb 插件，NAS 上不新部署任何东西**——FreshRSS 与 mail-archiver
是 NAS 上已有的独立服务，插件从 PC 经局域网直接调它们的 API（两条路都实测通过）；交付的只有**链接**
（正文不搬，人自己点进去看）；微信全文抓取随这次转向整个退役（人自己点 `mp.weixin.qq.com` 链接就是正常浏览，
不会触发风控）。原先计划的 nas-app 容器作废，水位与每轮的归档存进插件自己的数据文档。

## 验收

- [ ] RSS：经 FreshRSS 的 greader API（ClientLogin + stream/contents）取增量；关注哪些源在设置项里登记（feed id 会随 FreshRSS 重建而变，配置说明里要写明这一点）
- [ ] 邮件：经 mail-archiver 的 REST API（Bearer、按 id 倒序分页）取增量；发件人噪音名单可配置（初版为空，看到烦的再加）
- [ ] 水位：两边各记一个已处理到的最大 id（存在插件的数据文档里），本地这一轮的归档写进磁盘才算提交；宁可重复不可遗漏（至少一次）
- [ ] 转发去重：认出「//转发自:」「//@」前缀，两个来源互相转发的重复只留一条
- [ ] 精选：调 `deepseek.chat`，输入条目的元数据（标题 / 发件人 / 主题 / 短摘要），输出 picked `[{id, reason}]`——**只选不改写**，正文永远是来源的原文
- [ ] 降级：模型失败时改用规则精选（按噪音名单过滤后全部列出），照常归档，这一轮标 `curated_by: rules`；窗格上显示「模型连续降级 N 轮」
- [ ] 阅读器：一轮一个列表 `{来源, 标题, 链接, 一句理由}`；橘鸦早报的链接每天置顶；没选上的折叠成一个计数；邮件条目链到 mail-archiver 的网页（单封邮件能不能直接链接还没核实，不能的话点开时经 API 取正文就地展开）
- [ ] 打开外部链接：写 `target="_blank"` 或调 `window.open(url)`，内核交给系统默认浏览器；不带 `target` 的链接在工作台页面里点了没有反应（内核 0.7 的导航限制）
- [ ] 刷新：打开窗格就拉 + 开着时每小时刷一次 + 手动按钮
- [ ] 没有新内容时明确显示「无更新」，不调模型
- [ ] 在隔离 home 里走一遍真实链路（真取数 + 真精选 + 连跑两轮，验水位往前走与「无更新」这条路）
- [ ] `pnpm check` 全绿

## 方案

取数 → 按水位过滤 → 去重 → 精选（`deepseek.chat`）→ 这一轮归档（插件的数据文档，按日分组）→ 窗格列表。
DeepSeek 的 key 不在本插件，经 deepseek 插件调。初始关注的源：橘鸦（feed/3）、黑鸦（feed/20），都是
B 站动态源（经 FreshRSS）；邮件第一次运行时水位从当前最大 id 起，不回头总结积压——水位的含义
沿用 ugreen-nas-config `.god-flow/drafts/news-digest.md` 的设计，只是提交点从「推送成功」改成
「本地归档写进磁盘」。
